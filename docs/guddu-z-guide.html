    1. Project overview

    What

    An Android app that answers questions, solves maths, helps you study and reads photos. It works offline first and uses the internet only when it is available and you allow it.

    Goals and non-goals

    GoalNot a goal (for now)
    Private: your notes stay on your phoneTraining our own model from scratch
    Works in airplane modeMatching Google on live, up-to-date facts offline
    Honest: shows sources and confidenceiOS (later, maybe)
    Own brand: purple-pink-cyan cloud look, Guddu Z logoRunning a 7B+ model on a phone
    Analogy: the app is a small restaurant. The UI is the dining room, SQLite is the pantry, and the on-device AI is the chef. No food is delivered from outside, because everything is cooked locally.

    2. Key terms

    TermMeaning in plain words
    SLM / LLMA small (or large) language model: a program that predicts the next words, like very advanced autocomplete. SLMs are already trained; we do not train them.
    Quantization (Q4)Storing the model's numbers with less precision so the file is smaller. Like saving a photo as a smaller JPEG: a little quality lost, a lot of space saved.
    .ggufThe file format used by llama.cpp for quantized models.
    EmbeddingA list of numbers that represents the meaning of a text, so we can find "similar meaning" text.
    RAGRetrieval-Augmented Generation: search the library first, then let the AI answer from what was found.
    HallucinationThe AI says something false in a confident tone.
    OCRReading text out of a photo.
    Dev ClientA custom build of your app that includes native AI libraries. Expo Go cannot run them.
    EAS BuildExpo's online build service. It builds the Android app in the cloud, so you do not need to install Android Studio just to build.

    3. Architecture

    One screen, one router, four tools, one small local model.

    User input (text or photo)
        |
     ROUTER  (decides the type of question)
        |
 +------+-----------+--------------+
 |      |           |              |
Lookup  Maths      Study helper   Image
(RAG)   (LLM +     (LLM + notes)  (OCR first)
        mathjs)
        |
 Small local model (.gguf via llama.rn) writes the explanation
        |
 SQLite: notes, chat history, knowledge pack, embeddings

    Online / offline decision

    Question -> internet? no  -> offline pipeline
                      yes -> needs fresh info? no  -> offline (private, free)
                                               yes -> ask permission -> web search -> model summarizes -> show sources
    1. Offline is the default; online is an upgrade.
    2. Always show a badge: Offline or Online.
    3. Ask permission before anything leaves the phone.
    4. If the connection drops, fall back to offline without crashing.

    5. Android device tiers

    Phones are like water tanks: a 4 GB phone cannot hold what a 12 GB phone can. The app reads the phone's RAM and recommends a tier.

    Lite, about 4 GB RAM. ~1B model at Q4 (roughly 0.7-1 GB file). Basic quality, slower. Use a short context size.
    Standard, about 6-8 GB RAM. 1B-3B at Q4. The main target for most users.
    Plus, 8 GB+ RAM. 3B-4B class at Q4. Best quality, more heat and battery use.
    These sizes are rough guides. Android and other apps use RAM too, so a 6 GB phone does not have 6 GB free. Speed differs a lot between chips. Measure on your own phone. Plan on CPU first; treat GPU as a bonus to test later.

    6. Features in detail

    A) Google-like answers (RAG over a knowledge pack)

    1. User asks a question.
    2. Embed it and find the 3-5 closest chunks in SQLite.
    3. Prompt: "Answer using only this text."
    4. Show the answer plus the source title.
    5. If nothing matches, say "I couldn't find this" instead of guessing.

    Chunks are about 200-400 words each. Offer downloadable packs (Science, History, General). Check real pack sizes and licences (for example Kiwix offline Wikipedia) before promising anything.

    B) Maths solver (LLM explains, engine calculates)

    Language models slip on arithmetic, so the exact answer always comes from mathjs.

    Given:    2x + 6 = 14
Required: value of x
Method:   isolate x
Steps:    2x = 14 - 6 = 8   ->   x = 8 / 2 = 4
Answer:   x = 4
Check:    2(4) + 6 = 14  (verified by the engine)
    import { evaluate } from 'mathjs';
const x = evaluate('(14 - 6) / 2'); // 4, exact

    If the model's answer and the engine disagree, show the engine's answer.

    C) Study helper

    Explain at a chosen level, summarize notes, make quizzes and flashcards. Use fixed prompt templates (Explain, Quiz, Summarize) so every answer has the same shape and is easy to revise.

    D) Image input

    NeedToolWeight
    Read a printed questionOCR (ML Kit)Light
    What object is this?MobileNet or EfficientNet via ONNX Runtime / TFLiteLight
    Explain this diagramSmall vision-language modelHeavy

    Build OCR then model first. Handwritten maths is hard, so let users edit the scanned text before solving.

    7. Confidence trace

    Every answer shows a percentage, a colored bar and a "Why?" breakdown.

    SignalWhere it comes from
    Library matchEmbedding similarity between the question and the best chunk
    Matches sourceA check that the answer stays within the retrieved text
    Model certaintyToken probabilities, if llama.rn exposes them (verify)

    Starting formula (tune it by testing): confidence = 0.4 x match + 0.3 x support + 0.3 x certainty

    Worked example: 0.4 x 92 + 0.3 x 90 + 0.3 x 81 = 36.8 + 27 + 24.3 = 88.1, shown as 88% (High).

    Colors: green 75% and above, orange 40-74%, pink below 40%.

    Common mistake: treating the percentage as a guarantee. A small model can be confidently wrong, so low match always means "I don't know".

    8. Setup with EAS (online builds)

    Commands are a starting point. Check the current Expo docs, because templates and flags change.

    Step 1: create the project

    npx create-expo-app@latest guddu-z --template blank-typescript
cd guddu-z
npx expo install expo-dev-client

    Step 2: sign in and configure EAS

    npm install -g eas-cli
eas login
eas build:configure

    Step 3: development build for Android

    In eas.json, the development profile needs the dev client turned on:

    {
  "build": {
    "development": { "developmentClient": true, "distribution": "internal" },
    "production": {}
  }
}
    eas build --profile development --platform android

    Install the resulting APK on your phone, then run npx expo start --dev-client to load your code into it.

    You must rebuild the dev client every time you add a library with native code (like llama.rn). Changing only JavaScript does not need a rebuild.

    Step 4: phone preparation

    Turn on Developer Options and USB debugging. Test on a real phone, never only on an emulator.

    12. Common mistakes and risks

    MistakeFix
    Model too big for the phoneOffer tiers and auto-recommend
    Trusting the model for arithmeticAlways verify with mathjs
    Promising "Google-level" answers offlineSay "answers from your offline library"
    Using Expo GoUse a dev client built with EAS
    API keys inside the appUse your own small backend as a middleman
    Model stays loaded in the backgroundUnload when the app is backgrounded
    Phone gets hot or drains batteryCap tokens, add a cooldown
    Testing only on a good phoneKeep one budget phone as the worst case
    "Wi-Fi connected" assumed to mean "internet works"Also handle failed requests
    Big model files inside the Play Store uploadDownload after install (check Play Asset Delivery limits in Google's docs)

    13. Quick revision summary

    • SLMs are already trained: we add prompts, a library and tools, not training.
    • Google-like offline = RAG over a knowledge pack, with sources.
    • Maths = model explains, mathjs calculates, code verifies.
    • Images = OCR first, classifier second, vision model last.
    • Hybrid = offline first, online boost, with a badge and permission.
    • Confidence = match + source support + model certainty.
    • Builds = EAS dev client; rebuild after adding native libraries.
    • Test on a real, weak phone; manage memory, battery and heat.
